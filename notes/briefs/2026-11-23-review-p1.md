## Common rules

- **Review only.** Do not edit, commit, stash or run anything that writes
  in the worktree except your own report file. No sub-agents. No push,
  pull request or tag.
- **Probes** (a test you write to measure a claim) only in your own copy:
  `git -C /home/markus/Dokumente/GitHub/go-ha2fabric-review archive 5eefc0a | tar -x -C <your scratch dir>`;
  run `go test` there. Three reviewers share the worktree; a probe file in
  it breaks the others' builds. Name the probe in the finding and paste its
  output line.
- `go`, `golangci-lint` and the tools need `PATH=$HOME/go/bin:$PATH`.
- Read slices (`sed -n`, `grep -n`), not whole trees. Read the tests of
  the code you review: a missing negative case is a `test` finding.
- Every fact `file:line` at `5eefc0a`; references at their pin
  (`gf:`, `ui:`, `hm:`, `core:`, `sup:`, `hub:` prefixes). Measured (M:
  read, or a probe ran) and inferred (I) apart.
- Finding shape, one block per finding: **ID**, **severity**
  (high / medium / low / note), `file:line`, the claim, the reference line,
  M/I, the proposed fix, the red regression test that would prove it.
  Severity by consequence for this daemon's roles (decision 11 and 19:
  Home Assistant trusted, its data not; a commissioned controller reaches
  only the exposed entities' services; LAN and co-installed add-ons
  untrusted).
- Do not re-report a phase 0 row (`phase-0-register.md`) unless its fix is
  wrong or incomplete — then say so, citing the row.
- **Held back.** A security item that is open (an exploitable weakness, not
  a note) goes into `held/phase-1-<unit>.md` (untracked; `held/` is in
  `.git/info/exclude`); the committed report names it by ID and severity
  only. Phase 0's held reports (`held/threat-model.md`,
  `held/phase-0-verify.md`, `held/phase-0-premerge.md`) are context for S;
  never copy their content into a tracked file. Wording in tracked files
  follows decision 21: describe the admin check as it is, not the
  condition before it.
- A defect inside go-fabric, go-fabric-ui or go-hamapping is reported as an
  `upstream` candidate (theme `adpt`), with the pinned line, not worked
  around.
- Report ends with: counts per severity, what you did **not** read and why,
  the probes you ran, questions for the owner (with your recommendation).
- Stop when your report is written. Do not wait for, start or poll
  background work.

ID ranges: S `HR-P1-<theme>-01..29`, G-A `30..59`, G-B `60..89`, the
verifier none (it re-grades).

## Unit G-A — the plan side (Opus)

Report `notes/review/2026-11-23/phase-1-GA.md`. Files: `internal/plan`,
`internal/bridge`, `internal/adapt`, `internal/expose`,
`internal/exposure` (about 2 700 lines) and their tests.

1. `plan`: purity and determinism (map order, stable sort), overrides,
   `diff` correctness (an endpoint renamed, moved, re-typed, removed and
   re-added), input validation.
2. `bridge`: the reconciler against go-fabric's node API at v0.25.0
   (endpoint add/remove, attribute writes, the lock order, what happens
   while a controller is subscribed, a failed apply half-way), camera and
   command wiring.
3. Controller command → `adapt` → `call_service`: list every domain,
   service and data key a controller can make Home Assistant receive; is it
   bounded to the exposed entity and its services (decision 11); value
   conversions and clamps (after HR-P0-data-01's fix), units, rounding,
   unknown or out-of-range arguments.
4. `expose` and `exposure`: the Assist rule, labels, what is exposed when
   the selection is missing, empty or corrupt; agreement with `selection`.
5. Hostile entity data into go-fabric attributes: lengths and encodings
   (NodeLabel 32 bytes, other string attributes), what is cut, where.

## Unit G-B — the daemon side (Opus)

Report `notes/review/2026-11-23/phase-1-GB.md`. Files: `cmd/ha2fabric`
except the web/admin wiring of `main.go`, `supervisor.go`, `warnings.go`
(S reads those; read them only for context), `internal/ha/subscription.go`,
`fanout.go`, `snapshot.go`, and how this repository calls go-hamapping
(decision 9: boundary only).

1. `main.go`: start order, shutdown order and timeouts, exit codes,
   signals, what a failed component does to the rest.
2. `nodes.go`: the registry fleet — create, delete, rename, restart of a
   node; per-node goroutines and their end; `NODE_LIMIT`; concurrent web
   writes against a running resync.
3. `subscription`, `fanout`, `snapshot`: subscription life cycle across
   reconnect, a slow or dead consumer, unbounded queues, resync after a
   reconnect (missed events), the snapshot's consistency.
4. The go-hamapping boundary: every call, the types it carries, what this
   repository assumes about its output (ordering, uniqueness, lengths); a
   defect there is an issue candidate for go-hamapping.
5. Goroutine and context leaks (the inventory lists every `go` statement):
   each one's end.
