## Common rules

- **Review only.** Do not edit, commit, stash or run anything that writes
  in the worktree except your own report file(s). No sub-agents. No push,
  pull request, issue or tag.
- **Probes** only in your own copy:
  `git -C /home/markus/Dokumente/GitHub/go-ha2fabric-review archive 2324fbf | tar -x -C <your scratch dir>`;
  run `go test` there. Three reviewers share the worktree; a probe file in
  it breaks the others' builds. Name the probe in the finding, paste the
  failing line, and keep the probe file's text in your report's appendix
  (the fix wave reuses it as the red test).
- `go`, `golangci-lint` and the tools need `PATH=$HOME/go/bin:$PATH`.
- Containers (X1 only, if a measurement needs them): `docker` is available. Name every container,
  network and image you create with the prefix `p2x1-`, and remove them
  all before you stop (`docker ps -a --filter name=p2x1-`, the same for
  networks and images); never touch other containers or networks. No live
  Home Assistant (decision 12): fixtures (`internal/ha/hatest`) only.
- Read slices (`sed -n`, `grep -n`), not whole trees.
- Every fact `file:line` at `2324fbf`; references at their pin
  (`gf:`, `ui:`, `hm:`, `core:`, `sup:`, `hub:` prefixes). Measured (M:
  read, or a probe ran) and inferred (I) apart.
- Finding shape, one block per finding: **ID**, **severity**
  (high / medium / low / note), the flow (hop by hop, `file:line` each),
  the claim, the reference line, M/I, the proposed fix, the red regression
  test (the probe). Severity by consequence for this daemon's roles
  (decisions 11 and 19: Home Assistant trusted, its data not; a
  commissioned controller reaches only the exposed entities' services;
  the LAN and co-installed add-ons untrusted).
- Do not re-report a phase 0 or phase 1 row unless its fix is wrong or
  incomplete — then say so, citing the row.
- **Held back.** A security item that is open (an exploitable weakness, not
  a note) goes into `held/phase-2-<unit>.md` (untracked; `held/` is in
  `.git/info/exclude`); the committed report names it by ID and severity
  only, with no hint of its condition, its attacker or its path. That
  holds for every sentence of the tracked report, the questions included
  (phase 1's lesson: hints leaked through decisions and briefs, not only
  reports). The held reports of phases 0 and 1 (`held/*.md`) are context;
  never copy their content into a tracked file. Wording in tracked files
  follows decision 21: describe the admin check as it is, not the
  condition before it.
- A defect inside go-fabric, go-fabric-ui or go-hamapping is reported as an
  `upstream` candidate (theme `adpt`), with the pinned line, not worked
  around (decision 9 for go-hamapping: boundary only).
- Report ends with: counts per severity, what you did **not** read and why,
  the probes you ran (pass/fail), questions for the owner (with your
  recommendation), the probe appendix.
- Stop when your report is written. Do not wait for, start or poll
  background work.

ID ranges: X1 `HR-P2-<theme>-01..29`, X2 `30..59`, X3 `60..89`, the

## Unit X1 — the network (Fable)

Report `notes/review/2026-11-23/phase-2-X1.md` (+ `held/phase-2-X1.md`).
Start at `internal/web`, `cmd/ha2fabric/main.go` (web and admin wiring),
`cmd/ha2fabric/supervisor.go`, `internal/config`, `script/run.sh`,
`addon/config.yaml`, both Dockerfiles; go-fabric-ui's handler at its pin.

1. An unauthenticated client against the web listener **in each mode**:
   the add-on (host network, Ingress), the container image (loopback by
   default since decision 27; and with `-e WEB_LISTEN=… WEB_ALLOW=…`),
   stand-alone, `WEB_ADMIN`. Per mode: which routes answer, which write;
   measured with a real listener (`httptest` or the binary) and a table.
2. **The held row of phase 1** (decision 24): measure it. Its claim and
   the measurement to make are in `held/phase-1-S.md` and
   `held/phase-1-verify.md`. The result (confirmed with what it needs, or
   refuted) goes to `held/phase-2-X1.md`
   only; the tracked report says "(held) HR-P1-auth-01: measured, see the
   held report" and nothing more.
3. T2: a LAN peer forging the proxy's source address — state the argument
   and, where the setup allows, measure it.
4. T7 DNS rebinding and T8 a hostile origin against a stand-alone daemon
   and the image: Host and Origin checks, the custom header, as wired by
   this host (go-fabric-ui's own review owns its handler; here: what this
   host passes and whether it can be bypassed through this host's
   wiring).
5. T9 framing as this host configures it; what the owner's live Ingress
   test must check (a question, not a finding, where it needs Home
   Assistant's frontend).
6. The Matter port's reach into `call_service`: from an uncommissioned
   peer on the LAN (commissioning window, the passcode of decision 14,
   what is reachable before commissioning) to a write in Home Assistant.
7. Phase 0 and 1 fixes on this path (`HR-P0-auth-20`, `-cfg-22`,
   `-ha-23`/`-ha-31`, `HR-P1-cfg-12`, `-test-16`): do they hold under an
   adversary, not only under their tests.

## Unit X3 — life cycle and flows (Opus)

Report `notes/review/2026-11-23/phase-2-X3.md`. Start at `cmd/ha2fabric`
(`main.go`, `nodes.go`, `supervisor.go`), `internal/ha` (client,
subscription, fanout, snapshot), `internal/bridge`, `internal/camera`,
`internal/nodes`, `internal/selection`.

1. Reconnect: the Home Assistant connection drops mid-sync, mid-command,
   mid-camera session; the back-off of decision 28; what is resubscribed,
   what is resynced, what is lost (missed events).
2. `Fanout` and resync under load: a slow or stuck consumer, a burst of
   state events during a resync, the owed sync of `HR-P1-conc-32`.
3. The registry fleet end to end: create, delete, rename, restart, erase
   (`HR-P1-err-94`, `-err-101`, `-conc-93`) concurrently with a sync and
   with web writes; `NODE_LIMIT`.
4. The camera session's end (decision 31's idle end, a failed re-offer,
   the controller gone, the Home Assistant subscription's end) and the
   session's resources.
5. Shutdown: decision 29's one deadline with work in flight on every
   path; goroutine and subscription leaks — every `go` statement of the
   inventory and its end, measured with a probe where it is not obvious
   (`goleak`-style counting in your copy is fine).
6. The write flows end to end: a controller's command → bridge queue →
   adapt → `call_service` → Home Assistant's answer → the attribute;
   a web write (selection, node settings) → store → resync → node. What
   happens on each error on the way (fail open, swallowed, retried).
7. T15's life-cycle half: hostile text in errors that cross goroutines
   into logs and the status.
