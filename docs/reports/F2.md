## Per section

### Forget on registry remove — `e6ab16b`, `2e87889`

- `Bridge.Event` decodes `entity_registry_updated`; on action `remove` the
  worker records the entity's stable key (`noteRemoved`, from the last
  snapshot: device UID, `/`, registry entry id), and the next sync calls
  `node.Batch.Forget` for it — instead of `Remove` when the bridge serves
  it, on its own when it does not (disabled, hidden, unexposed). Logged
  `bridge.forget` (`entity`, `key`).
- An entity re-created before that sync (within the debounce) is in the
  plan again and is not forgotten.
- Home Assistant facts at 2026.10.3: remove event data
  `entity_registry.py:171-175`; `async_remove` keeps the entry id in
  `deleted_entities` `:1728-1775`; re-creation restores it `:1624`.
- `hatest`: `RemoveEntity`, `RestoreEntity`.
- Test `TestRemovedEntityIsForgotten`: a disabled and re-enabled plug keeps
  its number; a removed and re-created plug gets a fresh one; a disabled
  light removed and re-created gets a fresh one.

## Differences (from the issue)

- A removal and re-creation within one debounce window keeps the number
  (the entity is in the plan again when the sync runs). Documented in
  `docs/operations.md`.
- A removal event dropped by a full work queue (`bridge.queue_full`) is not
  forgotten; the re-sync that follows keeps the number.

## Questions

- **Q1.** Should a removal and re-creation within the debounce also forget
  the number? Doing that would mean a forget and an add for the same key
  in one batch. The issue does not cover this case.
