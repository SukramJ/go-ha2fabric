## HA client

`internal/ha` — coder/websocket, one reader per connection, ids increasing
per connection under the write lock, results to their caller, events of our
subscriptions to the handler; ping every 30 s (an unanswered ping drops the
connection); reconnect with back-off 1 s doubling to 60 s, reset after an
authenticated connection; after every (re)connection the bridge reads
everything again. The token is in memory only: sent in the auth message,
never logged (tests assert it in the client's, the daemon's and the
dump's logs).

## Composition

`internal/bridge`, after go-fabric's cookbook: `NodeConfig` (§2: listen,
passcode, discriminator, vendor/product, label, store, the daemon's logger,
the health probe at `node.DefaultProbeInterval`, the daemon's version as
SoftwareVersion; everything else go-fabric's default); `node.New` then
`Start` before the HA client runs, `Stop` after (§6). One worker goroutine:
each sync reads everything, applies the exposure rule, groups the exposed
entities by HA device, `hamapping.Map` per device, keeps a device whose
description signature is unchanged and `Build`s the others, then one
`Aggregator().Batch` (§4) removes vanished devices, `Replace`s the endpoints
of a changed device under their stable keys (`Remove`/`Add` for the
difference) and adds new ones, `MarkComplete` once; every state then goes
through `Plan.Apply` (§5). `state_changed` applies one state; when the
entity's description moved (a capability attribute) or the entity is new,
a re-sync follows (debounced, 1 s; registry events too).
`Plan.OnChange` queues into a second goroutine that turns each
`model.Command` into its `call_service`; a failed call puts HA's state back
onto the endpoint. Reachability: `Plan.Apply` from availability; on a
dropped HA connection every device `SetReachable(false)`; the re-sync on
reconnect restores each (§6). Pairing codes to the log (`ha2fabric.pairing`),
the web UI and `/api/health` (§7). A device go-fabric refuses to build
gets no endpoint; its entities' verdicts say "go-fabric refused the
device: …".

## Differences (from the brief)

- **Description from the state, not the registry.** The brief names
  `device_class`/`original_device_class` and the registry's unit;
  `config/entity_registry/list` carries neither (`as_partial_dict`,
  `helpers/entity_registry.py:369-403`). The state's attributes have the
  effective values (`helpers/entity.py:1131-1176`), so the adapter reads
  them there; `config/entity_registry/get_entries` (extended) is not used.
- **The adapter states WebSocket attributes under the catalog's MQTT
  names** (`hvac_modes` → `modes`, `min_color_temp_kelvin` → `min_kelvin`,
  `hs_color` → `color.h/.s`, `color_temp_kelvin` → `color_temp` with
  `color_temp_kelvin: true`). The rows read the MQTT JSON vocabulary; Q3
  asks go-hamapping to state the contract.
- **Area registry** is read for the device's SuggestedArea and the UI;
  nothing maps it (left out, below).
- **`get_config`** is read too: a climate's temperatures are in the
  installation's unit (`components/climate/__init__.py:296-316`).
- **Web UI port** in the add-on is 8486 (`ingress_port`), not 8099: on the
  host's network a common port collides with other host-network add-ons.
- **Registry events need no administrator** (`auth/permissions/events.py:30-49`);
  only `homeassistant/expose_entity/list` does (`exposed_entities.py:414-418`).
- **The release workflow** keeps the sibling's form (`make release`, the
  notes from the changelog) and adds the version check; images stay in
  their own workflows as in go-zendure2mqtt.
- **No `icon.png`/`logo.png`** in `addon/` (the sibling has one); the
  Supervisor shows its default.

## Decisions

- **Exposure rule** as the brief decides it; a stateless registry entry is
  no candidate yet ("no state yet").
- **Stable key** is go-hamapping's: `<device UID>/<entity_id>`, the device
  UID the HA registry id. A renamed entity id therefore renumbers its
  endpoint (Q4).
- **Unknown is unreachable** (the brief's `Available`): a sensor in
  `unknown` shows unreachable rather than a stale value.
- **Re-plan per device**: a device whose entities' descriptions are
  unchanged keeps its plan and endpoints; a changed one is rebuilt and
  `Replace`d under the same stable keys, so endpoint numbers survive.
- **A failed `call_service`** re-applies HA's current state to the
  endpoint; the controller sees the truth.
- **Token from the environment only**; no flag, so it never shows in a
  process list.
- **Web UI allow list** (`WEB_ALLOW`) instead of binding to the hassio
  bridge address: the add-on cannot know that address, the filter is the
  Ingress rule as written.
- **`backup: cold`** for the add-on: go-fabric's operations guide asks for a
  consistent copy of the store.
- **QR encoder written for the page** (byte mode, level M, versions 1–6),
  held by a golden test against python-qrcode's matrices, rather than an
  image dependency.

## Questions

- **Q1 (go-fabric kit / go-hamapping row).** A cover without
  `SET_POSITION` (features OPEN|CLOSE, a garage door) maps to
  `cover/window_covering` with features `Lift` only, and go-fabric
  `v0.11.0`'s `device.New` refuses it: `cover: FeatureMap names features
  this server does not serve: 0x1, the server serves 0x5, 0x12 or 0x17`.
  Needed: the kit's WindowCovering server serving Lift without
  PositionAwareLift (`device` / `cluster/spec/windowcovering`), or the row
  declaring `PositionAwareLift` always (go-hamapping `rows/cover.yaml`).
  Workaround: the device gets no endpoint; its verdict says why
  (`internal/bridge.build`, `internal/adapt` test case "garage").
- **Q2 (go-fabric facade).** A daemon-composed `node.New` cannot join a
  `fabrictest` site; the end-to-end test runs the bridge on
  `fabrictest.Device.Node()`. Needed: go-fabric's CJ (a site that takes a
  host's `node.Config`, e.g. `fabrictest.Topology.Config func() node.Config`).
- **Q3 (go-hamapping).** The rows read the MQTT JSON vocabulary
  (`state.color_temp` with `extra.color_temp_kelvin`, `state.color.h`,
  `extra.modes`, `extra.min_kelvin`, payload defaults from `mqtt.json`); a
  WebSocket source translates. Needed: a documented `Description.Extra` /
  `State` contract for a non-MQTT source (H1 Q3/Q4), or rows that also read
  HA's state attribute names (`hvac_modes`, `hs_color`,
  `min_color_temp_kelvin`).
- **Q4 (go-hamapping).** `Plan.options` derives the StableKey from
  `Entity.Key()`, which must be the entity id for `Apply`. Needed: a
  separate stable identity (`model.Basic` field or `hamapping.Map` option)
  so a renamed entity id keeps its endpoint (HA's registry `id` is stable).
- **Q5 (go-hamapping).** `model.Command` names the method by the MQTT
  topic prefix (`set_position`, `tilt`, `mode`, `temperature_low`,
  `oscillation`); the daemon's service table keys on these strings. Needed:
  exported method constants in go-hamapping (H1 Q5).
- **Q6 (go-hamqtt).** No typed capability set on `model.Description` (H1
  Q3): `supported_features`, `supported_color_modes`, `modes` travel in
  `Extra`.
- **Q7 (go-fabric).** `fabrictest.ReadCluster` of a removed endpoint returns
  no values and no error (a wildcard expands to nothing); a test that wants
  "the endpoint is gone" reads `fabrictest.Device.EndpointOf` instead.
  Needed: nothing, or a documented sentence in `testing-in-process.md`.

## by_design candidates

Compared against: home-assistant-matter-bridge is not local
(`../home-assistant-matter-bridge/` absent) and its GitHub repository
(`Nabu-Casa/home-assistant-matter-bridge`) answered "Repository not found";
so no comparison with it was possible. Compared against go-fabric's
cookbook and go-zendure2mqtt's embedding instead.

- **Exposure from Assist's list** rather than a bridge-own filter
  configuration: the installation's existing "Expose" setting decides, with
  include/exclude globs as the override.
- **Unknown state → unreachable** (the brief's rule), where a bridge could
  keep the last value reachable.
- **One bridged endpoint per mapped entity, grouped by HA device only for
  riders** (go-hamapping's form): a multi-entity HA device is several
  endpoints, not one composed device.
- **Devices removed when HA no longer exposes them**, unlike the cookbook's
  zendure daemon, which never removes a unit (cookbook §4).
